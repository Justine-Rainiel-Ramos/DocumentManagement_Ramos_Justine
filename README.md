# Document Management API

A RESTful ASP.NET Core Web API for uploading, retrieving, downloading, listing, and deleting documents. The application stores document metadata in SQL Server and physical files in the local filesystem.

## 1. Overview

The Document Management API provides endpoints for managing uploaded documents.

The application supports:

- Uploading documents with a maximum file size of 10 MB.
- Retrieving document metadata.
- Listing all uploaded documents.
- Downloading stored documents.
- Deleting documents and their associated files.
- Validating uploaded files and rejecting unsupported file types.
- Handling missing documents, invalid requests, and unexpected errors.

## 4. Installation and Setup

### Clone the repository

```bash
git clone https://github.com/Justine-Rainiel-Ramos/DocumentManagement_Ramos_Justine.git
cd DocumentManagement_Ramos_Justine
```

### Restore dependencies

```bash
dotnet restore
```

### Configure the database connection

Open `appsettings.json` and configure the connection string:

```json
{
  "ConnectionStrings": {
    "default": "Server=localhost;Database=DocumentManagement;Trusted_Connection=True;TrustServerCertificate=True;"
  }
}
```

Replace the server name with your SQL Server.

**Security note:** The connection string above is an example using Windows Authentication. Do not commit passwords, access tokens, or production credentials to the repository. For sensitive configuration, use .NET User Secrets or environment variables.

### Create the database

Install the Entity Framework Core CLI tool if it is not already installed:

```bash
dotnet tool install --global dotnet-ef --version 8.*
```

Create the initial migration:

```bash
dotnet ef migrations add InitialCreate --project DocumentManagement_Ramos_Justine/DocumentManagement.csproj
```

Apply the migration:

```bash
dotnet ef database update --project DocumentManagement_Ramos_Justine/DocumentManagement.csproj
```

The database and required tables will be created automatically.

### File storage configuration

Uploaded documents are stored locally in:

```text
DocumentManagement_Ramos_Justine/
└── Storage/
    └── Documents/
```

The storage directory is created automatically by the file storage service when the application starts.

Physical filenames are generated by the application rather than using user-supplied filenames directly.

## 6. API Endpoints

Base route: `/api/documents`

| Method | Endpoint | Description | Success Status |
|---|---|---|---|
| POST | `/api/documents` | Upload a document | 201 Created |
| GET | `/api/documents` | Retrieve all document metadata | 200 OK |
| GET | `/api/documents/{id}` | Retrieve specific document metadata | 200 OK |
| GET | `/api/documents/{id}/download` | Download a document | 200 OK |
| DELETE | `/api/documents/{id}` | Delete a document | 204 No Content |

### Upload a Document

**POST** `/api/documents`

Request content type: `multipart/form-data`

Form field:

| Field | Type | Required |
|---|---|---|
| File | File | Yes |

Maximum file size: 10 MB.

Supported extensions:

- PDF
- DOC / DOCX
- XLS / XLSX
- TXT
- PNG
- JPG / JPEG

### List Documents

**GET** `/api/documents`

Returns a list of uploaded documents and their metadata. Actual file contents are not included.

### Retrieve Document Details

**GET** `/api/documents/{id}`

Returns metadata for a specific document using its identifier.

### Download Document

**GET** `/api/documents/{id}/download`

Returns the physical document as a downloadable file.

### Delete Document

**DELETE** `/api/documents/{id}`

Deletes the document record and its associated physical file.

## 7. HTTP Status Codes and Error Handling

The API uses appropriate HTTP status codes to communicate request results.

| Status Code | Description |
|---|---|
| 200 OK | Request completed successfully |
| 201 Created | Document successfully uploaded |
| 204 No Content | Document successfully deleted |
| 400 Bad Request | Missing or invalid request data |
| 404 Not Found | Document or physical file does not exist |
| 413 Content Too Large | Uploaded file exceeds the 10 MB limit |
| 415 Unsupported Media Type | Unsupported uploaded file type |
| 500 Internal Server Error | Unexpected server-side error |

Errors are returned as JSON responses containing a descriptive message.

Example:

```json
{
  "message": "File size must not exceed 10 MB."
}
```

Unexpected exceptions are logged server-side, while clients receive a generic error message without internal implementation details.

## 8. Architecture and Implementation

### Architecture

The application follows a simple layered architecture that separates HTTP request handling, business logic, data access, and file storage responsibilities.

| Component | Responsibility |
|---|---|
| Controllers | Handle HTTP requests and responses |
| Services | Implement document management operations and business rules |
| Data | Provide database access through Entity Framework Core |
| Models | Define database entities |
| DTOs | Define request and response objects |
| Middleware | Handle exceptions and generate consistent error responses |
| Exceptions | Define application-specific exceptions |

### Data Access

Entity Framework is used with Microsoft SQL Server to store document metadata.

The `Document` entity contains:

- Document ID
- Filename
- Stored filename
- Content type
- File size
- Upload timestamp

### File Storage

Physical documents are stored in the local filesystem rather than directly in the database.

The application generates unique filenames using GUIDs to avoid filename collisions and prevent user-supplied filenames from being used as unrestricted filesystem paths.

The original filename is retained in the database for metadata retrieval and downloads.

### Error Handling

Custom exceptions and centralized exception-handling middleware are used to provide consistent HTTP error responses.

The upload process also attempts to remove the physical file if saving its corresponding database record fails.

## 9. Automated Testing

```bash
dotnet test DocumentManagement.Tests/DocumentManagement.Tests.csproj --logger "console;verbosity=detailed"
```

The service unit tests use an in-memory database and mocked file storage to isolate application logic from external dependencies.

## 10. Security Considerations

- Maximum upload size is enforced at 10 MB per file.
- Empty files and unsupported extensions are rejected.
- Server-generated filenames are used for physical storage.
- Filename validation helps prevent path traversal.
- `FileMode.CreateNew` prevents existing files from being overwritten.
- Uploaded files are stored outside publicly served directories.
- Sensitive credentials should be configured outside source control.
